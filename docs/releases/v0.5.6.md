## 安装

从本页 Assets 下载 `luyi0825-zcode-acp-0.5.6.tgz`，本地安装：

```bash
npm install -g ./luyi0825-zcode-acp-0.5.6.tgz
zcode-acp login      # 浏览器授权登录（一次性）
zcode-acp doctor     # 自检：Node / CLI 定位 / 登录态 / 模型列表
zcode-acp setup      # 自检 + 打印各客户端接入配置
```

`doctor --probe` 会实跑一轮 headless 对话做端到端验证。详细步骤见 [docs/usage-guide.md](https://github.com/luyi0825/zcode-acp/blob/main/docs/usage-guide.md)。

## 新增

### OpenIDEA 会话 fork（session/fork）

声明 ACP unstable 能力 `sessionCapabilities.fork` 并实现 `session/fork`：fork 把历史复制进独立新会话，后续 prompt 不影响原会话。OpenIDEA 按该声明启用 fork 入口（此前未声明，入口被禁用）。

zcode headless CLI 没有 fork 参数（`/fork` 仅 TUI 可用），fork 经 app-server（ZCode Protocol）走 ZCode Desktop 同款路径：`session/resume` 加载原会话，`session/fork` 按最后一条消息边界复制历史（无文件改动的纯对话会话同样可用）；新会话继承模型 / 思考档位 / 模式选择并落盘。空会话（还没跑过对话）fork 退化为新建；源会话正在执行或 fork 失败时明确报错，不静默降级成共享会话。

### 诊断日志（ZCODE_ACP_LOG）

bridge 跑在宿主进程树下，stderr 通常被宿主吞掉，宿主侧行为异常（如客户端不显示 agent 版本、会话突然中断）没有现场可查。现在设 `ZCODE_ACP_LOG` 指向目标文件即启用 NDJSON 追加式诊断日志，未设置整体 no-op（零开销）。

埋点覆盖：`initialize`（客户端与 bridge 双方版本）、每轮 `turn.start` / `turn.end`（spawn 参数、退出结果与耗时）、`records.full`（会话表满载淘汰失败）、`shutdown`（退出时清理的在跑轮次）、`prompt.error`（prompt 阶段异常）。目录自动创建，写失败仅在 stderr 提示一次，绝不影响会话本身；不做轮转，长期开启用外部工具截断。

## 修复

### 同一对话被重复创建出多个会话

zcodeSessionId（zcode CLI 真实会话 id）原先**只存 bridge 进程内存**，进程重启或记录被淘汰（上限 64）即丢。客户端 IM 多轮对话带着旧 ACP sessionId 调 `session/resume` / `session/load` 时，重建的记录拿不到 zcodeSessionId，下一轮 prompt 不带 `--resume` → zcode **新建会话**。表现为同一对话反复创建出多个标题相同的顶层会话（实测一份 MiCO 对话攒出 9 个重复会话），上下文也随之断裂。

现在新增 `session-store.js`，把续接状态按 ACP sessionId 落盘到 `~/.zcode-acp-sessions.json`：

- `session/resume` / `session/load` 内存未命中时，从落盘恢复 `zcodeSessionId` 与模型 / 思考级别 / 模式选择，续接不断、也不再新建重复会话；
- 状态变更时落盘：sessionId **首次落定**才写（一轮里几百个流式事件只写一次，模型流式热路径不碰文件），改模型 / 模式 / 思考级别时各写一次；
- 落盘是增强项，读失败 / 损坏一律降级回内存-only，绝不阻断会话本身。

健壮性与安全：null 原型对象承载映射，杜绝客户端 sessionId 用 `__proto__` / `constructor` 这类键触发原型污染；临时文件 + rename 原子替换，避免写一半崩溃留下半截 JSON；256 条上限按最旧淘汰，避免宿主长期复用下无限增长。

> 行为变更：之前文档把「重启丢映射 / 选择」列为已知限制，本版起改为落盘自动恢复（README 与 usage-guide 已同步）。修复只对**升级后的新对话**生效，已存在的重复会话不会追溯合并。

### 续接会话里累积出重复的 context.md 附件

MiCO 任务信封（`## Task Initiator … ## Human interaction …`）经 `splitTaskEnvelope` 拆出后，`runTurn` **每轮**都把它写成临时 `context.md` 并经 `--attach` 下发。而附件内容会**跨 `--resume` 持久保留**，续接轮再挂一份就在会话里累积出重复的 `context.md` 文件 part 与 Read 调用，信封正文随之重复（实测单会话攒出多个同名附件）。

现在信封附件**只在首轮（无 `--resume`）挂入**：附件跨 resume 保留，首轮挂一次即够全程使用，续接轮不再重挂，会话里不再多出重复 md 附件。

### Zed 里选不了模型

新版 ACP schema 的 `session/new` 响应已删除 `models` 字段，模型选择器改为 `configOptions` 里 `category: "model"` 的 select 选项，切换走 `session/set_config_option`。Zed 只读 `configOptions`，旧 `models` 字段被忽略，表现为模型下拉选不了（OpenIDEA 等走旧路径的宿主不受影响）。

现在 `configOptions` 同时声明模型选择器（仅本机有真实模型列表时，回退单模型不声明），`session/set_config_option` 接受 `configId: "model"`：校验、思考档位联动、落盘与广播规则与 `session/set_model` 一致；旧 `models` / `set_model` 路径原样保留。

### 宿主断开时在跑的 zcode 子进程成为孤儿

bridge 收到宿主断开（stdin end）即 `process.exit(0)`，正在跑的轮次不清理；POSIX 下 zcode 子进程自成进程组（detached），宿主杀 bridge 进程组也不会波及它——孤儿 zcode 继续跑完整个任务，继续消耗 token、改文件，用户却以为已中断。

现在 stdin end / SIGTERM / SIGINT 统一收口：先对 busy 会话逐个终止（杀整棵进程树，含工具调用拉起的孙进程），留 300ms 宽限（等 Windows 异步 taskkill 落地）再退出，并落 `shutdown` 日志。

### prompt 阶段的异常只回协议级 Internal error

`session/prompt` 里 `runTurn` 的启动失败（找不到 zcode CLI、provider 配置副本写盘失败）与图片校验抛错会一路冒泡，由 SDK 转成协议级 `Internal error (-32603)`，用户看不到任何定位信息；「请安装 ZCode Desktop / 设 ZCODE_HOME」「认证已过期请 login」这类既有指引文案根本到不了客户端。

现在统一在 handler 收口：错误消息原文发给客户端、返回 refusal，并落 `prompt.error` 日志。
